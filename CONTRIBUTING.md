# Совместная разработка

## Ветки
`main` содержит проверенную и запускаемую версию проекта. Каждая законченная задача выполняется в отдельной ветке:

- `feature/dynamic-programming` — новый алгоритм;
- `feature/plan-validation` — проверка расписаний;
- `feature/roundy` — исходный метод Roundy;
- `fix/input-validation` — исправление загрузки данных;
- `docs/model` — изменение постановки и документации.

Названия описывают изменение, а не номер недели или человека. Завершённую ветку можно удалить после объединения; следующая задача начинается от обновлённой main.

## Обычный рабочий цикл
После клонирования общего удалённого репозитория:

```bash
git switch main
git pull --ff-only origin main
git switch -c feature/plan-validation
```

Внесите изменения, выполните относящиеся к ним проверки, затем:

```bash
git status
git add <пути-к-изменённым-файлам>
git commit -m "Добавить проверку расписания поставок"
git push -u origin feature/plan-validation
```

Замените выражение в угловых скобках реальными путями. Указывайте в коммите только файлы своей задачи. После push откройте pull request из рабочей ветки в main и назначьте другого участника проверяющим.

## Что указать в pull request
- Какую проблему решает изменение.
- Что изменилось в поведении программы.
- Какие команды и примеры использованы для проверки.
- Меняется ли модель, формат входа или результата.
- Известные ограничения и незавершённые части.

Объединяйте изменение после проверки другим участником и устранения замечаний. Проверяющий сверяет код, документацию и контрольные примеры. Не объединяйте код, который ломает текущий запуск.

## Изменение общей модели
Порядок событий, смысл ёмкости, расчёт затрат и конечные условия сначала обсуждаются командой. Затем согласованно обновляются docs/model.md, версия модели, контракт данных, примеры и затронутые реализации. Изменение формата не вносится только в один решатель.

## Минимальная проверка текущей версии

```bash
python run.py instances/01_basic.json
python run.py instances/02_tight_capacity.json
python run.py instances/03_infeasible.json
```

Все три файла должны успешно загрузиться. Эти три команды проверяют только структуру входа. Проверка расписаний и автоматические тесты:

```bash
python run.py instances/01_basic.json --plan examples/01_basic_plan.json
python -m unittest discover -s tests -v
```

При добавлении алгоритмов набор проверок расширяется содержательными контрольными случаями.

## Данные и результаты
Входные задачи не содержат ожидаемых ответов. Ручные планы находятся отдельно в examples/ и не объявляются оптимальными. Для экспериментов сохраняйте параметры, версию кода, среду и начальное значение генератора. Автоматически полученные результаты не добавляйте все подряд: для отчёта сохраняйте выбранные воспроизводимые сводки и команды их получения.

## Первое размещение проекта
Владелец команды создаёт пустой удалённый репозиторий и предоставляет доступ остальным. Если проект получен из ZIP, в его корне выполните `git init -b main`; при уже существующем Git-репозитории повторная инициализация не нужна. Настройте в Git собственные имя и почту, проверьте файлы и создайте первый коммит:

```bash
git add .
git commit -m "Добавить начальную структуру проекта"
git remote add origin <адрес-общего-репозитория>
git push -u origin main
```

Адрес в угловых скобках замените реальным URL. Остальные участники клонируют этот репозиторий. Рекомендуется включить защиту main с требованием pull request и одного одобрения. Эти настройки нужно отдельно включить на выбранной платформе; локальные файлы их не применяют.
