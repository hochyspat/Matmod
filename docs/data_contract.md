# Формат задачи и результата

Формат обмена — JSON в UTF-8. Это текст с парами «название поля: значение». Массив хранит значения по периодам в порядке от первого до последнего.

## Основная серия и расширения
Для основной серии все элементы demand одинаковы, а initial_inventory и terminal_inventory равны нулю на обоих узлах. Массив спроса и явные поля запасов оставлены для будущих расширений. Текущий загрузчик проверяет структуру и типы: успешная загрузка не подтверждает принадлежность экземпляра основной серии, допустимость расписания или поддержку экземпляра будущим решателем.

## Задача
| Поле | Тип | Значение |
|---|---|---|
| schema_version | строка | `1.0` |
| model_id | строка | `serial_inventory_v1` |
| instance_id | строка | Уникальное имя экземпляра |
| horizon | целое > 0 | Число периодов |
| demand | массив целых ≥ 0 | Спрос, длина равна horizon |
| capacity.warehouse | целое ≥ 0 | Вместимость склада |
| capacity.retailer | целое ≥ 0 | Вместимость магазина |
| initial_inventory | объект | Начальные warehouse и retailer |
| terminal_inventory | объект | Точные конечные warehouse и retailer |
| costs.order_warehouse | число ≥ 0 | Фиксированная стоимость внешнего заказа |
| costs.order_retailer | число ≥ 0 | Фиксированная стоимость перемещения |
| costs.hold_warehouse | число ≥ 0 | Хранение единицы конечного складского остатка |
| costs.hold_retailer | число ≥ 0 | Хранение единицы конечного остатка магазина |

Поле model_id ссылается на порядок событий из model.md. Новая семантика требует новой версии модели. Метаданные с ожидаемыми ответами находятся отдельно от входных данных, чтобы алгоритмы не могли их использовать как подсказку.

## Результат решателя
- `schema_version`, `model_id`, `instance_id`: ссылка на формат и задачу.
- `algorithm`: название метода.
- `status`: `optimal`, `feasible`, `infeasible_proven`, `no_solution_found`, `time_limit`, `error`.
- `has_plan`: есть ли план, который нужно проверить. При лимите времени план может быть найден, но не доказан оптимальным.
- `orders`: массив q по периодам или null при отсутствии плана.
- `transfers`: массив x по периодам или null при отсутствии плана.
- `reported_cost`: стоимость по расчёту решателя или null.
- `message`: пояснение, в том числе причина ошибки или остановки.

`optimal` и `infeasible_proven` требуют обоснования точным методом. Эвристика, не нашедшая решения, возвращает `no_solution_found`, а не доказанную недопустимость.

Допустимые ручные планы в examples/ используют тот же формат; название алгоритма `manual_reference`, статус `feasible`. Файл `02_over_capacity_plan.json` — намеренно неверный результат: проверка должна отвергнуть его заявление о допустимости.

## Отчёт независимой проверки
Реализован в validation.py. Отчёт содержит `valid`, `cost_matches`, `accepted`, `violations`, `trace`, `recomputed_cost`, `cost_difference` и `optimality_checked`. Подробная семантика, значения null и коды завершения описаны в [validation.md](validation.md). Проверка восстанавливает запасы по действиям, не доверяя запасам решателя. При отсутствии плана она не проверяет доказательство недопустимости задачи; допустимый план не означает доказанную оптимальность.

Время работы измеряет общий запуск вокруг вызова решателя. Предлагаемый запуск не включает чтение файла, независимую проверку и построение графиков; окончательные правила измерения утверждаются до экспериментов. Версия кода и среда сохраняются вместе с результатами.

## Изменения формата
Формат обновляется согласованно с моделью, примерами и реализациями. Текущая версия формата — `1.0`, модели — `serial_inventory_v1`.
