# Независимая проверка расписания

Модуль `src/inventory_project/validation.py` реализует правила `serial_inventory_v1`. Он принимает задачу и готовый план, восстанавливает движение товара и пересчитывает стоимость. Алгоритмы ДП и Roundy ему не нужны. Их будущие планы будут проверяться тем же способом.

## Запуск
Из корня проекта (на Windows можно использовать `py` вместо `python`):

```bash
python run.py instances/01_basic.json --plan examples/01_basic_plan.json
python run.py instances/02_tight_capacity.json --plan examples/02_tight_capacity_plan.json
python run.py instances/02_tight_capacity.json --plan examples/02_over_capacity_plan.json
```

Первые две команды подтверждают стоимость 20 и 24. Третья должна обнаружить переполнение склада в первом периоде: в склад вместимостью 2 пытаются принять 6 единиц. Это специально неправильный план, а не неисправность программы.

Для сохранения подробного отчёта:

```bash
python run.py instances/01_basic.json --plan examples/01_basic_plan.json --output results/basic_validation.json
```

Без `--plan` сохраняется прежний режим просмотра экземпляра. Отчёт не может перезаписать входной файл задачи или плана.

## Порядок проверки
1. Проверить структуру задачи, принадлежность плана экземпляру и версии модели, типы и длины массивов действий.
2. Проверить начальные запасы относительно ёмкостей.
3. В каждом периоде принять внешний заказ и проверить ёмкость склада до отгрузки.
4. Проверить наличие товара для перемещения.
5. Добавить перемещение в магазин и проверить его ёмкость до спроса.
6. Проверить возможность удовлетворить спрос и вычислить конечные остатки.
7. Начислить фиксированные затраты только за положительные поставки, хранение — по конечным остаткам.
8. Проверить заданные конечные запасы, сложить затраты и сопоставить с reported_cost.

При первом физическом нарушении проверка останавливается. В trace остаются корректные предыдущие периоды и доступные сведения о нарушенном периоде. Неопределённые значения равны null. Стоимость всего недопустимого плана не вычисляется, чтобы отрицательные остатки не создавали фиктивную экономию.

## Результат функции validate_plan
| Поле | Смысл |
|---|---|
| valid | true — действия допустимы; false — есть нарушение; null — плана нет |
| cost_matches | Совпадает ли reported_cost с независимым расчётом; null, если сравнение не проводилось |
| accepted | true — допустимый план с подтверждённой стоимостью; false — план или стоимость не прошли проверку; null — плана нет |
| violations | Первое обнаруженное нарушение с кодом и периодом |
| trace | Запасы, действия и затраты по проверенным периодам |
| recomputed_cost | Суммарная пересчитанная стоимость допустимого плана |
| cost_difference | Заявленная стоимость минус пересчитанная |
| optimality_checked | Всегда false: оптимальность не проверяется |

Физически допустимый план с неверной стоимостью получает valid=true, cost_matches=false и accepted=false. Для сравнения чисел используется math.isclose с относительной и абсолютной погрешностями 1e-9.

Если has_plan=false, программа не подтверждает и не опровергает утверждение решателя об отсутствии допустимого решения. Если status=optimal, проверяется только сам план, а не доказательство оптимальности. Форматные ошибки вызывают ValueError и выводятся командной строкой как ошибка входа.

Периоды в trace и violations нумеруются с 1. Номер 0 обозначает начальное состояние.

## Коды завершения команды
- 0 — успешный просмотр задачи либо допустимый план с правильной стоимостью.
- 1 — нарушение ограничений или несовпадение стоимости.
- 2 — ошибка формата, чтения или записи файла.
- 3 — результат не содержит плана; математическая допустимость задачи неизвестна этой проверке.

## Автоматические проверки

```bash
python -m unittest discover -s tests -v
```

Набор включает ручные стоимости, хранение на обоих узлах, проверку ёмкости до расхода, нехватку товара, конечные условия, неправильные действия и стоимость, отсутствие плана и отсутствие проверки оптимальности.

## Использование в будущих алгоритмах
Вызов: `validate_plan(instance, plan)`. Instance — словарь задачи, plan — словарь результата из data_contract.md. Функция не изменяет входные словари. Авторы решателей сохраняют существующие поля и передают действия без использования внутренних расчётов проверяющего модуля для формирования решения.

Проверяющий модуль умеет пройти по массиву известного спроса и явно заданным начальным запасам согласно тем же балансам. Это не утверждение о поддержке расширенных экземпляров будущими алгоритмами; основная серия проекта остаётся постоянным спросом и нулевыми граничными запасами.
